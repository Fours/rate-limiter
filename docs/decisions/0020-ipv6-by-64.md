# 0020. IPv6 clients are grouped by /64, and IPv4-mapped addresses count as IPv4

- **Status:** Accepted
- **Date:** 2026-11-07
- **Milestone:** 4

## Context

`defaultIdentify` falls back to `req.ip` when a request has no API key and no user. An ISP or host usually hands one subscriber a whole IPv6 /64, which is 2^64 addresses. Keyed on the full address, a client could use a new address for every request and get a new limit each time. Separately, a server listening on `::`, Node's default where IPv6 is available, sees every IPv4 client as an IPv4-mapped address (`::ffff:1.2.3.4`), so the same client got a different ID depending on how the server listened. Behind `trust proxy`, Express passes `X-Forwarded-For` through as sent, so one address can reach `req.ip` written many ways.

## Decision

`defaultIdentify` normalises `req.ip` before using it:

- **IPv4** stays as it is: `ip_203.0.113.7`.
- **IPv4-mapped IPv6**, in either form (`::ffff:203.0.113.7` or `::ffff:cb00:7107`), becomes the IPv4 address it carries: `ip_203.0.113.7`.
- **Any other IPv6** becomes its /64, written in RFC 5952 form: `ip_2001:db8:1:2::/64`. Brackets and a zone (`%eth0`) are dropped first, and case, leading zeros and `::` placement don't matter.
- **A value that isn't an IP** is kept as it is, as before.

IPs stay readable rather than hashed: they aren't secrets the way API keys are ([0002](0002-hash-api-keys.md)). The prefix length is fixed. A caller who needs something else passes their own `identify`.

## Alternatives considered

| Option | Why not |
| --- | --- |
| Keep the full IPv6 address | One host can rotate through its /64 and never be limited |
| A shorter prefix, such as /56 or /48 | Some home ISPs delegate a /56 or /48 per customer, but mobile networks give each device its own /64 out of a shared block, so a shorter prefix would put unrelated subscribers in one bucket. /64 is the smallest block a subscriber reliably gets. |
| A configurable prefix length | Another option for a rare need. A custom `identify` already covers it. |
| Leave IPv4-mapped addresses as they are | The same IPv4 client would keep two IDs, depending on whether the server listens on `::` or on an IPv4 address |
| Hash IPs, as API keys are | They're not secrets, and readable keys make Redis and logs easier to debug |

## Evidence

- **The probe** ([data/0020-req-ip-probe-2026-11-07](data/0020-req-ip-probe-2026-11-07/results.md), Express 5.3.0): on a `::` listener an IPv4 client's `req.ip` is `::ffff:127.0.0.1`, and on an IPv4 listener `127.0.0.1`. With `trust proxy`, `X-Forwarded-For` reaches `req.ip` unchanged: uppercase, leading zeros, `[brackets]`, `%zones` and both mapped forms.
- **Unit tests** (`test/identify.test.ts`): addresses in one /64 share an ID and addresses in different /64s don't; compressed, expanded, uppercase, bracketed and zone-suffixed forms of one address give one ID; IPv4 keeps today's ID, and both mapped forms give the same one; values that aren't IPs pass through.
- **Through Express** (`test/identify.express.test.ts`): a real app shows a direct IPv4 client of a dual-stack server arriving mapped and getting `ip_127.0.0.1`, a direct `::1` client getting `ip_::/64` (skipped where the machine has no IPv6 loopback), and the forwarded forms collapsing to one ID per /64 behind `trust proxy`.
- Breaking each part on purpose failed a test: keeping the whole address, a /56 prefix, leaving mapped addresses as IPv6, keeping brackets, keeping zones, compressing the wrong run of zeros, and `defaultIdentify` ignoring the normalised form. Keeping zones passed at first, because a zone touches only the last group, which is outside any /64. A mapped address with a zone, `::ffff:203.0.113.7%eth0`, now catches it.

## Consequences

- **Storage keys change once, on upgrade,** for two groups of clients, who start with a full limit: IPv6 clients, now keyed by /64, and IPv4 clients of a server listening on `::`, whose keys were `ip_::ffff:…` and are now plain IPv4. Old keys expire on their own TTLs. Clients identified by API key or user are unaffected, and so are IPv4 clients of an IPv4-only server. This lands before the first npm release (milestone 5), so no published version is affected.
- **Everyone in one /64 shares a limit.** That's one subscriber in the usual case, but it can be several devices behind one router, as with IPv4 NAT today.
- The README's Identifying clients section describes the grouping and the one-time change.
